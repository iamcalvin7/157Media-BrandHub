Root Cause Investigation
Task 1 — How Replit's migration validator works
The migration reference document is explicit on this point:

"When the user clicks Publish, the publish flow:
1. Introspects both the development and production databases.
2. Computes a SQL diff between them."*

This is a live database introspection diff — not migration file replay. Replit connects to both the dev and production databases, reads their current structural state (tables, constraints, indexes, column definitions), and generates DDL SQL to bring production up to parity with dev.

The migration .sql files in lib/db/drizzle/ are never read by the publish flow. They are read only by drizzle-kit migrate, which runs in the dev environment via post-merge.sh. They play no role in what Replit sends to production.

Task 2 — Why the UPDATE in 0003_keen_tyrannus.sql is not considered
The prepended UPDATE is in a migration file. The publish flow never opens that file. Here is the exact sequence of what happens on Publish:

Replit publish validator:
  1. Introspects dev DB   → finds FK constraint present on brand_voice_notes.source_post_id
  2. Introspects prod DB  → finds FK constraint absent
  3. Generates diff SQL:
       ALTER TABLE "brand_voice_notes"
       ADD CONSTRAINT "brand_voice_notes_source_post_id_content_posts_id_fk"
       FOREIGN KEY ("source_post_id")
       REFERENCES "public"."content_posts"("id")
       ON DELETE set null ON UPDATE no action;
  4. Validates the diff against existing production rows
       → finds bvn.id=45, 84, 85 with source_post_id values not in content_posts
       → FAILS: foreign key violation
  5. Aborts. Publish blocked.
  ← lib/db/drizzle/0003_keen_tyrannus.sql is never opened.
  ← lib/db/drizzle/0001_data_cleanup_d2a.sql is never opened.

The UPDATE in 0003 would only help if drizzle-kit migrate were the publish mechanism. It is not.

Task 3 — Exact contents of both files confirmed
lib/db/drizzle/0001_data_cleanup_d2a.sql (lines 29–35):

-- 3. Null-out brand_voice_notes.source_post_id orphan references.
--    Rows bvn.id=84,85 reference source_post_id=48 which no longer exists.
UPDATE brand_voice_notes
SET    source_post_id = NULL
WHERE  source_post_id IS NOT NULL
  AND  source_post_id NOT IN (SELECT id FROM content_posts);

lib/db/drizzle/0003_keen_tyrannus.sql (lines 1–25) — the prepended UPDATE is intact:

-- Production data repair: null-out any remaining orphan source_post_id references.
-- [...]
UPDATE brand_voice_notes
SET    source_post_id = NULL
WHERE  source_post_id IS NOT NULL
  AND  source_post_id NOT IN (SELECT id FROM content_posts);
--> statement-breakpoint
ALTER TABLE "brand_voice_notes" ADD CONSTRAINT
  "brand_voice_notes_source_post_id_content_posts_id_fk"
  FOREIGN KEY ("source_post_id")
  REFERENCES "public"."content_posts"("id")
  ON DELETE set null ON UPDATE no action;

Both files are correct and intact. Neither is the problem. The problem is they are the wrong tool for this mechanism.

Task 4 — Why validation still fails despite the repair SQL
Three compounding facts explain the failure completely:

Fact 1 — The schema source of truth is brandVoiceNotes.ts line 10, not the migration files:

source_post_id: integer("source_post_id")
  .references(() => contentPostsTable.id, { onDelete: "set null" }),

This TypeScript declaration is what the dev database's FK constraint was built from. It is what Replit introspects when it reads the dev DB. It is the source of the diff SQL. The migration files are a record of how the dev DB got to its current state — not what the publish flow reads.

Fact 2 — drizzle-kit migrate never ran on production:
All three orphan rows (45, 84, 85) still exist in production. 0001_data_cleanup_d2a.sql contains a generic UPDATE that would catch all three. If drizzle-kit migrate had ever applied 0001 to production, rows 84 and 85 would be gone. They are not. This confirms the publish flow has never replayed any migration file against production.

Fact 3 — The publish validator validates the DDL before any DML can run:
Even if Replit did read migration files, the FK diff SQL it generates and validates is treated as a single-step schema change. FK constraint validation in PostgreSQL checks all existing rows at the moment the ALTER TABLE ADD CONSTRAINT is executed — there is no mechanism to interleave a preceding DML UPDATE into the validation step of a separately-generated DDL statement.

Task 5 — The correct fix for Replit's deployment system
The root constraint is: production data must be clean before the publish validator generates and applies the FK diff SQL. The only way to clean production data within Replit's model is to get a write operation to execute against the production database before the FK is included in the diff.

There are two viable paths, both are two-publish sequences:

Path A — Remove FK, publish, clean data via deployed app, re-add FK, publish again
Publish 1 (unblocking publish):

Remove .references(() => contentPostsTable.id, { onDelete: "set null" }) from brandVoiceNotes.ts line 10
Run drizzle-kit generate → new migration drops the FK from dev DB
Apply migration to dev: FK removed from dev DB
Dev and prod are now at parity on this constraint (neither has it)
Diff is empty for this column → publish succeeds with all other pending changes
Data repair (between publishes):
6. Once the app is running in production, add a temporary one-request admin endpoint (protected by Clerk + admin role check) that executes the UPDATE against the production DB

Call that endpoint once — 3 rows are nulled
Remove the endpoint from code
Publish 2 (re-adding the FK):
9. Re-add .references() to brandVoiceNotes.ts

Generate migration → new migration adds FK back to dev DB
Apply to dev, verify
Publish — diff includes the FK again, but production data is now clean → succeeds
